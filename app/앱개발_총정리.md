# 불침번 앱 개발 총정리

> 발표자료 반영용. 개발 배경, 대시보드와의 기능적 차이, 개발 과정, 완성 기능, 향후 발전방향을 정리.

---

## 1. 왜 앱이 필요했는가 — 타깃과 문제의식

**타깃: 현장 점검인력(관리사, 소방안전관리자 등 실사·순회점검을 도는 사람)**

방재실 대시보드는 "누군가 상시로 화면을 지켜보는 관제 거점"을 전제로 설계됐다. 하지만 실제 소방시설 점검은 관리사가 건물을 돌아다니며 개별 설비를 눈으로 확인하고 점검표를 작성하는 방식으로 이뤄진다. 이 두 가지는 요구사항 자체가 다르다.

- 방재실 인원: 한 화면에서 6개 설비 전체 상태를 동시에 파악해야 함 → **대시보드**
- 현장 점검인력: 지금 눈앞의 이 설비 하나에 대한 정보가 필요하고, 점검했다는 사실을 기록으로 남겨야 함, 그리고 하루 점검분을 문서로 제출해야 함 → **앱**

즉 앱은 대시보드의 축소판이 아니라, **"현장에서 들고 다니며 개별 설비를 점검하고 그 행위를 기록·증빙하는 도구"**로 역할이 다르다. 이 프로젝트의 핵심 차별화(AI 기반 열화 추세 예측)는 대시보드가 담당하고, 앱은 그 결과를 현장에서 확인하고 법정 점검 업무(점검표 작성)를 보조하는 역할을 맡는다.

---

## 2. 대시보드와 앱의 기능적 차이

| | 방재실 대시보드 | 현장 앱 |
|---|---|---|
| 사용 주체 | 방재실 상주 관리자 | 순회 점검인력 |
| 화면 구성 | 6개 설비 전체 동시 표시 | 개별 설비 단위 진입 (QR/리스트) |
| 데이터 방향 | 읽기 전용 | 대부분 읽기 + 점검완료 시에만 쓰기 |
| 핵심 기능 | AI 열화 추세, 실시간 판정 | 점검 수행 기록, 이력 PDF 출력 |
| 접근 경로 | 상시 접속된 모니터 | QR 스캔 또는 앱 내 리스트 |
| 존재 목적 | 관제·조기경보 | 법정 점검 업무 보조·증빙 |

두 시스템은 **같은 라즈베리파이 서버를 바라보는 별개의 클라이언트**다. 앱과 대시보드가 서로 직접 통신하지 않고, 파이가 유일한 중앙 서버 역할을 하며 각 클라이언트는 파이의 API만 호출한다. 이 구조 덕분에 대시보드 쪽 기존 코드(센서 판정 로직, AI 모델)를 한 줄도 건드리지 않고 앱 기능을 독립적으로 얹을 수 있었다.

```
                [라즈베리파이 서버] — 유일한 데이터 소스
                ├─ 센서 데이터 수신 (기존, 안 건드림)
                ├─ 대시보드 페이지 렌더링 (기존, 안 건드림)
                └─ 앱 전용 API (신규 추가: 체크리스트/점검완료/PDF용 이력)
                        │
              ┌─────────┴─────────┐
              ▼                   ▼
        [방재실 대시보드]      [현장 앱]
        (읽기 전용)         (읽기 + 점검완료 쓰기 1건)
```

## 3. 완성된 기능 (예선 제출 기준)

- **QR 스캔**: 앱 내장 카메라로 설비별 QR 인식 → 해당 설비 상세화면 진입
- **설비 상세화면**: 대시보드 화면(WebView)을 그대로 로드해 실시간 센서값·AI 판정 확인
- **점검완료 기록**: 버튼 한 번으로 점검자·시각·상태를 서버에 저장
- **PDF 리포트**: 그날 점검완료된 설비들을 모아 하나의 통합 리포트로 출력, 점검완료→PDF 반영까지 실제 데이터로 연동 확인 완료
- **홈 화면 체크리스트**: 6개 설비 상태와 점검 여부를 한 리스트에서 확인 (현재는 상태값이 더미 데이터, 4번 항목에서 후술)

### 개발 과정에서의 주요 판단

- **QR 접근 제어**: 처음엔 URL 딥링크(커스텀 스킴)를 검토했으나, 앱 내장 QR 스캐너(`mobile_scanner`)가 이미 있어 이를 그대로 활용하는 쪽으로 단순화. 일반 카메라 앱으로 찍으면 텍스트만 인식될 뿐 앱과 연결되지 않아, 별도 스킴 등록 없이도 "앱을 통해서만 유효하게 동작한다"는 요구를 충족.
- **대시보드 통합 vs 분리**: 설비별로 대시보드를 쪼개 새 라우트를 만드는 방식도 검토했으나, 시간 제약상 **기존 통짜 대시보드 화면을 그대로 재사용**하고 앱이 그 위에 "현재 보고 있는 설비" 배너와 점검완료 버튼만 얹는 방식으로 확정. 대시보드(Flask) 코드는 한 줄도 수정하지 않음.
- **코드 격리 원칙**: 앱 연동용 API는 기존 센서/판정 로직과 완전히 분리된 새 파일(`inspection_api.py`)로 작성. 기존 코드와의 연결 지점을 최소화해 안전하게 병행 개발.

## 4. 아직 미완성인 부분 (결선 발전방향)

예선 제출 시점 기준으로, 시간상 다음 항목들은 의도적으로 보류했다.

1. **앱 아이콘 커스텀 이미지** — 현재 Flutter 기본 아이콘 사용 중
2. **PDF 한글 폰트 미적용** — 현재 PDF 출력 시 한글이 깨져 나옴 (데이터 자체는 정상 반영됨을 확인)
3. **점검이력 영구 저장 미비** — 현재 서버 메모리에만 저장되어 재시작 시 소실됨. 실서비스 전환 시 DB 저장 및 조회 시 날짜 범위 제한 로직 필요
4. **홈화면 실시간 자동 갱신 부재** — 현재는 화면 진입/탭 전환 시점에만 데이터를 새로 불러옴. 지속적으로 화면을 보는 상황에서 상태 변화가 자동 반영되지 않음
5. **QR의 역할 제한적** — 대시보드에 설비별 필터링 라우트가 없어, 현재 QR과 홈화면 리스트 진입이 동일한 통짜 화면으로 연결됨. 결선에서 Flask에 `/equipment/{id}` 라우트를 추가하면 QR이 "그 설비만 바로 보여주는" 진짜 필터링 진입점으로 격상됨
6. **홈화면 상태 표시가 실제 DB와 불일치** — 체크리스트 API가 현재 하드코딩된 더미 상태값을 반환 중이라, 실제로는 경보 상태인 설비가 앱에서는 정상으로 표시되는 경우 확인됨. 대시보드와 동일한 DB를 조회하도록 연동 필요 (결선 최우선 과제)

## 5. 발표자료 활용 포인트 제안

- **"왜 대시보드와 앱을 분리했는가"**에 대한 답으로 2번 항목의 표를 그대로 활용 가능
- **아키텍처 다이어그램**(파이 중심 구조)은 "기존 시스템 안정성을 해치지 않고 확장했다"는 근거로 사용 가능
- 완성 기능 데모(QR→상세→점검완료→PDF)는 "AI 판정 결과를 현장에서 바로 확인하고, 법정 점검 업무 부담을 줄인다"는 스토리로 연결
- 미완성 항목은 숨기기보다 "다음 단계 로드맵"으로 명시하면, 시간 제약 속에서도 시스템 전체를 설계적으로 사고했다는 인상을 줄 수 있음
