# 자탐1 루프저항 2층 판정 재조정 정리 (2026-08-16)

**작성일**: 2026-08-16
**대상**: 팀 공유용, 개발완료보고서 근거자료
**배경**: 자탐1 실물 하드웨어(5초 간격 전송) 기준 캘리브레이션·판정 로직 검증 중 발견된 문제들과 해결 과정을 순서대로 정리.

---

## 1. 오프셋(`LOOP_FIXED_OFFSET_OHM`) 실측 확정

가변저항을 "열화 없음" 위치로 완전히 돌린 상태에서 시리얼 모니터 raw 값을 실측 평균해 오프셋을 확정했다.

- 여러 차례 재측정을 거쳐 **`LOOP_FIXED_OFFSET_OHM = 230`**으로 최종 확정
- 노이즈로 raw 값이 오프셋보다 순간적으로 낮게 나올 수 있다는 것도 실측으로 확인됨(아래 §2의 클램핑 이슈로 이어짐)

---

## 2. 클램핑 위치 버그 — DB/회귀 계산과 화면 표시 분리 필요

### 증상
- 대시보드 보정저항이 음수로 표시되는 문제 발견 → `corrected = max(0, raw - offset)` 클램핑 추가
- **이 클램핑을 DB 저장·회귀분석 입력 단계에도 그대로 적용**했더니, raw가 노이즈로 오프셋보다 낮게 나온 샘플만 0으로 뭉개지고 높게 나온 샘플은 그대로 남는 **비대칭 왜곡**이 발생
- 이 비대칭 데이터에 선형회귀를 돌리자 실제로는 열화가 없는데도 인위적인 양의 기울기(가짜 열화 추세, `79.67 Ω/day`)가 나타났고, `LOOP_TREND_ALARM_SLOPE`(당시 2.0)를 훨씬 초과해 **가짜 alarm**이 발생

### 해결
클램핑은 **오직 사람이 보는 화면 표시에만** 적용하고, DB 저장값·회귀분석 입력값은 원본(음수 허용)을 그대로 사용하도록 분리했다.

- `server/judge/regression.py`: `corrected_ohm = raw_ohm - LOOP_FIXED_OFFSET_OHM` (클램핑 없음, 음수 허용)
- `dashboard/app.py`: `display_corrected_ohm = max(0, raw_ohm - LOOP_FIXED_OFFSET_OHM)` — 화면 표시 직전에만 적용, DB나 회귀 계산에는 전혀 영향 없음

---

## 3. 회귀 기울기(Ω/day) 노이즈 증폭 문제 발견

### 원인
`evaluate_loop_resistance`의 2층(추세) 판정은 최근 `LOOP_TREND_HISTORY_LIMIT`(당초 20)개 샘플로 선형회귀를 돌려 Ω/day 기울기를 낸다. 자탐1 실물은 `SEND_INTERVAL_MS=5000`(5초 간격)이므로, 20개 샘플은 겨우 **100초 분량**이다.

100초 동안의 아주 작은 정상 노이즈(1~2Ω)도 "하루 단위(Ω/day)"로 환산하는 과정에서 `86400/100 = 864배` 증폭되어, 임계값을 훨씬 초과하는 가짜 기울기(수백 Ω/day)가 발생하고 가짜 alarm이 뜬다.

기존 더미데이터 검증(1시간 간격 전송)이 이 문제를 못 잡은 이유는, 1시간 간격에서는 20개 샘플이 20시간치라 노이즈 증폭 배율이 훨씬 작았기 때문 — **검증 환경과 실물 하드웨어의 시간축이 달라 실물에서만 드러난 문제**였다.

---

## 4. 1차 재조정 — 다운샘플링 + 임계값(시연 3분 제약 하)

당시 목표: "시연 영상(3분) 안에 caution→alarm 전이를 보여줄 수 있으면서, 노이즈 오탐도 억제"라는 두 조건을 동시에 만족.

- **다운샘플링 도입**: `LOOP_TREND_DOWNSAMPLE_EVERY_N = 5` — raw 저장·1층(절대임계값) 판정·대시보드 실시간 표시는 그대로 5초마다 유지하면서, 2층(회귀) 이력에 넣는 샘플만 5개당 1개로 솎아냄 (실질 25초 간격)
- 다운샘플링만으로는 노이즈 오탐 목표(5% 이하)를 달성하지 못함 확인 (`LOOP_TREND_ALARM_SLOPE`=2.0 자체가 노이즈 표준편차 대비 지나치게 낮았음)
- `LOOP_TREND_ALARM_SLOPE`/`CAUTION_SLOPE`가 법정기준이 아니라 원래부터 "임시값, 실측 후 재조정 필요"로 설계되어 있던 값임을 확인 — 노이즈 분포 실측 기반으로 **700 / 230**으로 재조정
- 검증: D시나리오(5초 간격 순수 노이즈) alarm 오탐 억제 + B시나리오(사람이 포텐셔미터를 돌리는 시연용 가속 프로파일, `B_ACCEL_K`) caution→alarm 3분 내 전이, 둘 다 만족 확인

## 5. 결선 전용 2차 재조정 — 시연 3분 제약 해제

시연 영상에는 자탐 2층(추세) 판정 결과를 아예 노출하지 않기로 팀 결정 → "3분 내 반응" 제약이 사라지면서, 노이즈 억제만 최우선으로 재탐색.

### 변경된 값

| 상수 | 1차(시연 제약 有) | 2차(결선 전용, 최종) |
|---|---|---|
| `LOOP_TREND_DOWNSAMPLE_EVERY_N` | 5 | **100** |
| `LOOP_TREND_HISTORY_LIMIT` | 20 | **50** |
| 실질 회귀 시간창 | 25초 | **약 6.94시간** |
| `LOOP_TREND_MIN_SAMPLES` | 3 | **15** |
| `LOOP_TREND_ALARM_SLOPE` | 700 | **8** |
| `LOOP_TREND_CAUTION_SLOPE` | 230 | **3** |

### 재조정 근거
- D시나리오(자탐1 실물과 동일한 5초 간격 순수 노이즈)를 10회 반복 시뮬레이션(각 15,000패킷)해 steady-state 기울기 표준편차 `~0.45 Ω/day`, 99th percentile `~0.92 Ω/day`를 실측
- 이 분포를 넉넉히 벗어나는 값으로 `ALARM_SLOPE=8`/`CAUTION_SLOPE=3` 확정 → **D시나리오 alarm 오탐 비율 0%**(10회 반복 전부) 달성
- B시나리오도 "며칠~2주" 단위로 진행되는 실제 부식 속도를 반영해 재설계(7일 내 법정기준 도달 가속 프로파일) — **caution 약 2.32일째, alarm 약 6.42일째**로 순서대로 안정적 전이 확인. 즉 2층 판정이 1층(절대임계값) 도달보다 약 4일 먼저 조기경보를 준다.

---

## 6. 부수적으로 발견·해결한 DB 성능 문제

재조정 검증 중 B시나리오가 12만 건 이상의 패킷을 처리하는데, `fire_alarm_log`에 `node_id` 조회용 인덱스가 없어 테이블이 커질수록 사실상 O(n²)로 느려지는 문제를 발견했다.

- `schema.sql`에 `CREATE INDEX IF NOT EXISTS idx_fire_alarm_log_node_id ON fire_alarm_log(node_id, id)` 추가
- 검증뿐 아니라 **실제 운영 DB에도 반영** — 결선에서 장기간(수개월) 데이터가 누적돼도 조회 성능이 저하되지 않도록 사전 방지

## 7. 시연/결선 표시 분리 — `DEMO_MODE` 플래그

2차 재조정 값(반응속도보다 정확도 우선)은 시연 짧은 스트림에서는 "표본부족"만 계속 뜨거나, 실물 하드웨어로는 결선용 숫자가 그대로 노출되어 시연 취지와 안 맞는다. 코드를 삭제/주석처리하는 대신 **플래그로 시연/결선을 전환**하도록 구현했다.

- `server/config.py`: `DEMO_MODE = True` (기본값, 시연 준비 기간 기준)
- `dashboard/app.py`: 카드 데이터에 `demo_mode` 필드 포함 — 값 자체(`loop_trend_slope_ohm_per_day`, `loop_rttf_days`)는 항상 그대로 계산·전달
- `dashboard/templates/index.html`: "열화 추세"/"잔여 고장시간 예측" 두 줄만 `{% if not c.demo_mode %}`로 조건부 렌더링. **`status`(normal/caution/alarm) 배지는 그대로 노출** — 1층 절대임계값 판정까지 같이 가려지지 않도록 유지

**결선 전환 시 필수 작업**: `server/config.py`의 `DEMO_MODE`를 `False`로 변경.

## 9. 핵심 교훈

1. **화면 표시용 클램핑과 저장/계산용 원본 데이터는 반드시 분리**해야 한다 — 표시 단계에서만 다듬고, 회귀분석 입력은 원본을 그대로 둬야 통계적 왜곡을 피할 수 있다.
2. **검증 시뮬레이션의 시간축이 실제 하드웨어와 다르면, 실물에서만 나타나는 문제를 검증 단계에서 놓칠 수 있다** — 반드시 실제 배포 조건(전송 주기)과 동일한 시간축으로도 별도 검증해야 한다.
3. **Ω/day처럼 "짧은 관측을 긴 시간 단위로 환산"하는 계산은 관측 시간창이 좁을수록 노이즈가 기하급수적으로 증폭**된다 — 임계값 설계보다 시간창의 절대 길이가 먼저 검토돼야 하는 변수다.
4. **"임시값, 재조정 필요"라는 주석은 실제 재조정 시점에 놓치지 않고 챙겨야 한다** — 처음부터 계획된 절차였고, 이번에 정확히 그 시점에 대응했다.
5. **시연용 반응성과 결선용 정확도를 하나의 상수로 동시에 만족시키기 어려운 경우, 값 절충보다 "시연에서 이 기능을 보여줄지 여부"부터 먼저 결정**하는 게 더 깔끔한 해법이었다.
