## 1. 배경 — 왜 이 로직인지

자탐1은 `zone_type = "differential"`(차동식)로, 절대온도가 아니라 **온도 상승 속도(℃/min)** 로 화재를 판정해야 합니다. 근거는 "감지기의 형식승인 및 검정기술기준" 제14조(차동식스포트형감지기의 감도시험):

| 종별 | 작동해야 함 (T, ℃/min) | 몇 분 이내 (M) | 작동하면 안 됨 (t, ℃/min) | 몇 분간 (m) |
|---|---|---|---|---|
| 1종 | 10 이상 | 4.5분 | 2 이하 | 15분 |

즉 **10℃/min 이상 상승 → 화재로 판정**, **2℃/min 이하 상승은 15분 지속돼도 오작동 금지**가 설계 목표입니다. 절대온도 고정값(예: "25℃ 넘으면 경보") 방식은 정온식 로직이라 쓰면 안 되고, 반드시 "속도" 기준이어야 합니다.

**중요한 개념 정리 (§7과 연결됨)**: "부작동시험 판정로직"과 "작동시험 판정로직"은 서로 다른 두 개의 알고리즘이 아닙니다. `evaluate_temp_rise_rate()` **하나의 임계값 함수가 상시로 돌면서** rate가 낮으면 normal, 높으면 alarm을 내는 것뿐이고, 이 하나의 함수가 양쪽 기준(2℃/min 이하는 조용히, 10℃/min 이상은 반응)을 동시에 만족하도록 설계된 겁니다. "부작동시험"과 "작동시험"은 이 상시 로직에 서로 다른 물리적 자극(느린 상승 vs 빠른 상승)을 줘서 **결과를 검증하는 절차**일 뿐, 로직 자체가 두 개로 나뉘는 게 아닙니다.

## 2. 노드에서 오는 데이터 (펌웨어 이미 반영 완료)

`fire_alarm_differential_node.ino`가 5초마다 아래 필드를 UDP JSON으로 보냅니다 (이미 배포됨, 추가 하드웨어 작업 없음):

```json

  "node_id": "fire_zone_differential_01",
  "device_type": "fire_alarm",
  "zone": "차동식구역",
  "zone_type": "differential",
  "seq": 123,
  "ts": 1755900000.0,
  "boot_id": 3921847123,
  "loop_resistance_ohm": 213.4,
  "temp_c": -27.1,
  "temp_rise_rate": 0.02,
```

**⚠️ 지금 서버는 `temp_raw_adc`, `temp_v`, `boot_elapsed_ms` 를 그냥 버리고 있습니다** (패킷 파서/스키마 미반영). 그리고 **`temp_c`/`temp_rise_rate` 값 자체가 지금은 의미 없는 임시식으로 계산된 값**입니다(예시처럼 마이너스로 나옴) — `TEMP_V_MIN/V_MAX/C_MAX` 상수가 아직 검증 전 placeholder라서 그렇습니다. **판정 로직은 `temp_c`/`temp_rise_rate`가 아니라 `temp_raw_adc`(또는 `temp_v`)를 직접 써서 raw 단위로 계산해야 합니다** — 아래 §4의 계수로 변환하기 전까지는 절대 `temp_c`를 신뢰하지 마세요.

### 3-3. 판정 함수 신설 — `server/judge/` 안에 (예: `differential.py` 또는 기존 `regression.py`에 추가)

`evaluate_loop_resistance()`와 같은 위치·패턴으로 신설. **이 함수는 상시로 돕니다 — 점검모드 여부와 무관하게 항상 계산됩니다** (§7에서 바뀌는 건 이 결과를 "어떻게 다룰지"뿐).

```python
# 캘리브레이션 회귀식 (잠정치 — §4 참고, 작동시험 데이터로 최종 확정 예정)
TEMP_RAW_PER_C = -170.0   # raw 1℃당 변화량 (음수 = 온도 오르면 raw 감소)

# 20~30초(4~6샘플, 5초 간격) 이동창으로 rate 계산 — 5초 단일 샘플로 하면 안 됨
RATE_WINDOW_SAMPLES = 5   # 25초 창

# 제14조 1종 기준을 raw/윈도우로 환산 (아래 §4의 최종 계수로 업데이트 필요)
ALARM_RAW_DROP_PER_WINDOW = 500   # 잠정치 — 10C/min 이상에 해당하는 raw 하락폭

def evaluate_temp_rise_rate(recent_raw_samples):
    """
    recent_raw_samples: 최근 RATE_WINDOW_SAMPLES개의 (timestamp, temp_raw_adc) 튜플, 시간순
    반환: "normal" | "alarm"
    항상 상시로 호출됨 — 점검모드와 무관하게 동일하게 동작.
    """
    if len(recent_raw_samples) < RATE_WINDOW_SAMPLES:
        return "normal"

    oldest_raw = recent_raw_samples[0][1]
    newest_raw = recent_raw_samples[-1][1]
    raw_drop = oldest_raw - newest_raw

    if raw_drop >= ALARM_RAW_DROP_PER_WINDOW:
        return "alarm"
    return "normal"
```

**주의**: `recent_raw_samples`는 노드가 이미 중앙값 필터를 적용해서 보낸 `temp_raw_adc` 값입니다(펌웨어 반영 완료 — 단일 ADC 읽기가 아니라 10회 측정 중앙값).

## 4. 임계값 — 아직 잠정치입니다, 오늘 데이터로 확정 필요

지금까지 실험(무반응시험 + 부작동시험 2회)으로 나온 raw↔℃ 회귀는:

- 1차 부작동시험(간헐적 버스트, 참고용): raw ≈ -150.3×℃ + 12003.5 (R²=0.879)
- 2차 부작동시험(고정저출력, 노이즈 스파이크 있음): raw ≈ -191.2×℃ + 12963.3 (R²=0.513)

노이즈 스파이크 때문에 2차 회귀 신뢰도가 낮습니다. 중앙값 필터 적용 후 작동시험 데이터로 계수를 다시 뽑아 §3-3의 `TEMP_RAW_PER_C`, `ALARM_RAW_DROP_PER_WINDOW`를 최종 확정할 예정입니다(오늘 중 전달 예정).

## 6. 판정 결과 처리 — 왜 그냥 `trigger_alert()` 호출하면 안 되는가

지금까지 다른 엣지들(루프저항 등)은 `evaluate_*()` 결과가 alarm이면 바로 `dispatch/lcd_buzzer_output.py`의 `trigger_alert()`를 호출해서 실제 부저/LCD 경보를 내보내는 구조였을 겁니다. **자탐1(그리고 §7에서 다룰 다른 엣지들)은 이 부분에 한 단계가 더 필요합니다.**

이유: 자탐1의 정상 동작 검증(부작동시험/작동시험)은 **실제 열원을 갖다 대는 물리적 시험**입니다. 이 시험을 할 때마다 진짜 화재 경보(부저 울림, LCD "화재!" 표시)가 나가면, 실제 비상상황과 "우리가 지금 점검 중" 상황을 시스템이 구분 못 하게 됩니다. 실제 소방 수신기에도 "시험모드" 스위치가 있어서, 기사님이 감지기 시험기로 테스트할 때 회로/판정 로직은 평소와 똑같이 반응하지만 그 반응이 "진짜 화재 경보"로 나가는 대신 "시험 확인됨"으로만 기록되도록 되어 있습니다. 이 프로젝트에도 동일한 개념이 필요합니다.

## 7. 점검모드(Test Mode) — 신규 설계, 중요

### 7-1. 핵심 원칙

- **판정 로직(`evaluate_*()`)은 절대 건드리지 않습니다.** 점검모드든 아니든 항상 똑같이 계산됩니다 — 이게 꺼지면 실제 화재도 못 잡는 위험한 시스템이 됩니다.
- **바뀌는 건 판정 결과를 "어떻게 처리할지"뿐입니다**: (a) 진짜 경보로 내보낼지, (b) 시험 기록으로만 로그에 남길지.
- **[2026-08-23 변경] 대시보드 버튼이 아니라 노드에 달린 물리 택트스위치로 구현합니다.** 통신 왕복(대시보드→서버→노드 명령 전달) 없이, 노드가 이미 5초마다 보내는 UDP 패킷에 버튼 상태를 필드 하나로 얹어서 보내는 방식입니다. 다른 엣지들도 명령 실행을 택트스위치로 하고 있어 일관된 패턴입니다. 서버는 그냥 매 패킷의 `test_mode` 필드를 읽기만 하면 되고, 별도의 커맨드 API(`start_test_mode()`/`end_test_mode()`를 서버가 외부에서 호출하는 구조)는 필요 없습니다.
- **[2026-08-23 변경] 시험 종류(부작동/작동) 자동 구분은 하지 않습니다.** 버튼은 "점검모드 ON/OFF" 토글 하나만 합니다. 어떤 시험이었는지, 합격인지는 나중에 로그 보고 사람이 판단합니다(자동 합격/불합격 판정 기능은 생략 — 시간 절약).

### 7-2. 펌웨어 쪽 구현 (자탐1/자탐2/소화기 공통 패턴)

노드 펌웨어(`.ino`)에 추가:

```cpp
const int TEST_MODE_PIN = 27;  // 실제 배선한 GPIO 핀 번호로 교체
bool testModeActive = false;
bool lastButtonState = HIGH;   // INPUT_PULLUP이라 평소 HIGH, 누르면 LOW

// setup()에 추가
pinMode(TEST_MODE_PIN, INPUT_PULLUP);

// loop() 매 반복 초입에 추가 (디바운스 포함)
bool buttonState = digitalRead(TEST_MODE_PIN);
if (buttonState == LOW && lastButtonState == HIGH) {
  delay(30);  // 디바운스
  if (digitalRead(TEST_MODE_PIN) == LOW) {
    testModeActive = !testModeActive;  // 누를 때마다 토글
    Serial.printf("점검모드 %s\n", testModeActive ? "시작" : "종료");
  }
}
lastButtonState = buttonState;
```

그리고 `sendPacket()`에 `doc["test_mode"] = testModeActive;` 한 줄만 추가하면 됩니다.

### 7-3. 서버 쪽 구현

버튼 상태가 패킷에 실려오므로, 서버는 상태를 따로 관리할 필요 없이 **매 패킷마다 그 안의 `test_mode` 값을 그대로 보고 분기**하면 됩니다:

```python
result = evaluate_temp_rise_rate(recent_raw_samples)
if packet["test_mode"]:
    log_test_event(zone_id, result, packet["ts"])  # 시험 기록용 로그만 남김 (진짜 경보 안 나감)
else:
    if result == "alarm":
        trigger_alert(zone_id)  # 평소엔 그대로 실제 경보
```

대시보드에는 그냥 "자탐1: 점검모드 중"이라는 표시와, `log_test_event`로 쌓인 로그를 시간순으로 보여주는 화면 정도만 있으면 됩니다(합격/불합격 자동 판정 없이, 로그만 보고 현서가 직접 해석). 시연 때 목걸이 이 표시가 켜져 있으면 "저희가 지금 점검 중입니다"를 시각적으로 보여줄 수 있어서 오히려 데모용으로도 괜찮습니다.

### 7-4. 이 로직이 다른 엣지에도 필요한가 — 검토 결과

같은 문제(실제 물리적 자극을 줘서 상시 로직을 테스트하면, 그 순간 진짜 경보가 나가버림)가 발생하는지 엣지별로 점검했습니다:

| 엣지 | 점검모드 필요 여부 | 이유 |
|---|---|---|
| **자탐1 (차동식)** | ✅ 필요 (본 문서 대상) | 열원 시험 시 상시 로직이 그대로 반응해서 실제 경보처럼 나감 |
| **자탐2 (광전식)** | ✅ 필요할 가능성 높음 | 구조가 자탐1과 동일 — 연기/가스 상시 분류 로직에 실제 발연원을 갖다 대는 시험을 하면 똑같이 진짜 경보가 나갈 것 |
| **소화기 (리프노드, MPU6500 이탈감지)** | ✅ 필요할 가능성 높음, **단 스위치 위치 결정 필요** | 이탈감지도 상시 로직이라 테스트하려고 들어올리면 즉시 "이탈 경보"가 나감. 리프노드 4개 각각에 스위치를 달지, 게이트웨이 1개에 달아서 "지금부터 전체 소화기 점검모드"로 서버가 4개를 한꺼번에 처리할지는 소화기 하드웨어 구조에 맞게 현서가 결정 필요(개별 4개보다는 게이트웨이 1개 권장 — 배선 부담 적음) |
| **유도등 (배터리/정전감지)** | △ 검토 권장 | 애니매틱 시연 스크립트에 "유도등 전원 차단 → 점등 유지" 장면이 있음 — 이때 정전 감지 알림이 있다면 동일 이슈 발생 가능. 다만 급하지 않으면 다음 순위 |
| **가스계 (CO2 중량손실)** | ❌ 낮은 우선순위 | 손실률 계산이 원래 며칠 단위 추세라, 순간적 자극-반응 시험 개념 자체가 약함 |
| **수계 (펌프 성능시험)** | 해당 없음(이미 구현됨) | 이미 성능시험 버튼(밸브 개폐로 체절/부하 전환)이 구현되어 있음 — 이 패턴이 애초에 참고 모델이었음 |

**권장사항**: 자탐1 하나에만 하드코딩하지 말고, `dispatch/lcd_buzzer_output.py`(또는 별도 `server/test_mode.py`)에 **엣지 공통으로 재사용 가능한 유틸리티**로 구현할 것을 권장합니다. 노드가 패킷에 `test_mode` 필드를 실어 보내므로, 서버는 상태를 따로 저장/관리할 필요 없이 매 패킷을 그대로 넘기기만 하면 됩니다:

```python
# server/test_mode.py (신규, 여러 엣지 공통 사용 — 상태 저장 불필요, 패킷값 그대로 사용)
def handle_judgment(zone_id, status, packet_test_mode):
    """evaluate_*() 결과와 패킷의 test_mode 값을 넘기면 알아서 분기 처리"""
    if packet_test_mode:
        log_test_event(zone_id, status)
    elif status == "alarm":
        trigger_alert(zone_id)
```

이렇게 만들면 자탐1/자탐2/소화기가 각자 `evaluate_*()` 결과 + 패킷의 `test_mode` 값을 이 `handle_judgment()` 하나에 넘기기만 하면 되고, 점검모드 로직을 엣지마다 중복 구현할 필요가 없습니다.
