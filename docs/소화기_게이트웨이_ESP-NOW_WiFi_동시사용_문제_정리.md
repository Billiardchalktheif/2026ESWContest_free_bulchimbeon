# 소화기 게이트웨이 — ESP-NOW·WiFi 동시 사용 문제와 해결 과정

> `docs/네트워크_인프라_장애요인_해결방안_정리.md`(라즈베리파이 핫스팟 인프라 문제 정리)와 이어지는 자료입니다. 그 문서에서 해결한 문제(WPA 프로토콜 협상 실패)를 반영한 뒤에도 소화기 게이트웨이만 별도로 WiFi 연결이 반복적으로 끊기는 증상이 남아있었고, 이를 추적한 과정과 최종 결정을 정리합니다.

---

## 배경

소화기 게이트웨이(`extinguisher_gateway.ino`, ESP32 DevKitC)는 리프노드 4개로부터 **ESP-NOW**로 가속도 데이터를 수신하고, 이를 **WiFi/UDP**로 라즈베리파이에 전달하는 역할을 한다. 즉 하나의 ESP32가 두 개의 무선 통신(ESP-NOW 수신 + WiFi STA 송신)을 동시에 처리해야 하는 유일한 노드다.

`네트워크_인프라_장애요인_해결방안_정리.md`에서 다룬 WPA 프로토콜 협상 문제를 해결한 뒤에도, 이 게이트웨이만 유독 WiFi 연결이 주기적으로 끊기는 증상이 계속됐다. 다른 노드(자탐1, 자탐2 등)는 동일한 핫스팟 환경에서 문제없이 안정적으로 동작해, 게이트웨이 특유의 원인을 의심하게 됐다.

---

## 원인 추적 과정

### 1차 가설: 라즈베리파이 WiFi 드라이버 자체의 결함

`dmesg`로 라즈베리파이 커널 로그를 확인한 결과, 아래 에러가 반복 발생하는 것을 확인했다.

```
brcmf_vif_set_mgmt_ie: vndr ie set error : -52
```

라즈베리파이 4 내장 WiFi 칩(Broadcom BCM4345/6)의 `brcmfmac` 드라이버가 AP(핫스팟) 모드에서 관리 프레임(vendor IE) 처리 중 겪는, 커뮤니티에 다수 보고된 알려진 결함이었다. `iw reg set KR`(규제 도메인 명시), 채널 변경(6→11) 등으로 완화를 시도했으나 완전히 해결되지는 않았고, 게이트웨이 외에도 노트북의 SSH 세션 자체가 같은 핫스팟에서 간헐적으로 끊기는 것을 확인해, **이 문제는 게이트웨이만의 문제가 아니라 라즈베리파이 AP 모드 자체의 공통 결함**임을 확정했다.

### 2차 가설: ESP-NOW와 WiFi STA의 동시 사용 충돌

라즈베리파이 쪽 완화 조치 이후에도 게이트웨이만 재현이 지속되어, ESP-NOW 코드를 제거한 WiFi 전용 테스트 버전을 별도로 만들어 비교했다.

- **WiFi만 사용(ESP-NOW 제거)**: 안정적으로 유지됨
- **ESP-NOW 재도입(리프노드 미연결 상태에서도)**: 동일하게 재현됨

리프노드로부터 실제 패킷을 수신하는지 여부와 무관하게, `esp_now_init()`을 호출하는 것 자체가 WiFi STA 연결을 불안정하게 만든다는 것을 확인했다. ESP32는 물리적으로 2.4GHz 무선 라디오가 하나뿐이라, ESP-NOW와 WiFi STA는 이 라디오를 시분할로 공유하는 구조적 제약이 있다. 채널 고정(`esp_wifi_set_channel()`), 초기화 순서 변경, `WiFi.setSleep(false)` 등 여러 완화책을 시도했으나 근본적으로 해결되지 않았다.

## 검토한 대안과 각각의 한계

| 방안 | 내용 | 한계 |
|---|---|---|
| USB WiFi 동글 교체 | 라즈베리파이 내장 `brcmfmac`를 검증된 칩셋(예: RT5572)의 동글로 대체 | 라즈베리파이 AP 모드 결함은 해결되지만, ESP-NOW+WiFi 동시 사용 충돌(게이트웨이 자체 문제)은 별개로 남음. 국내 배송 일정이 예선 제출 기한과 맞지 않아 채택 보류 |
| ESP32(ESP-NOW 전용)+ESP8266(WiFi 전용) 보드 분리, UART 유선 연결 | 게이트웨이 내부의 ESP-NOW/WiFi 충돌은 해결되나, ESP8266도 결국 라즈베리파이 AP에 WiFi로 붙어야 해 AP 모드 결함(1차 가설)의 영향은 그대로 남음 |
| 게이트웨이를 라즈베리파이에 USB Serial로 직결 (WiFi 완전 제거) | 게이트웨이의 WiFi 자체를 없애 두 문제 모두 회피 가능함을 확인 | 게이트웨이 개별 문제는 해결되지만, 나머지 4개 설비(자탐1·2, 수계, 가스계, 유도등)와 관리용 SSH는 여전히 라즈베리파이 AP 모드에 노출됨 — 근본 해결이 아닌 국소 우회 |

## 최종 해결 — 라즈베리파이를 AP 모드 대신 외부 공유기 클라이언트로 전환

라즈베리파이 자체 핫스팟(AP 모드) 대신, 외부 공유기(SJHOUSE)에 WiFi **클라이언트**로 접속하는 방식으로 전환했다.

```bash
sudo nmcli connection modify BulchimbeonAP connection.autoconnect no
sudo nmcli connection down BulchimbeonAP
sudo nmcli device wifi connect "<외부 공유기 SSID>" password "<비밀번호>"
```

`brcmf_vif_set_mgmt_ie` 에러는 **AP 모드 특유의 결함**이었기 때문에, 라즈베리파이가 클라이언트 모드로 동작하는 이 방식에서는 발생 조건 자체가 사라진다. 전환 이후 게이트웨이의 ESP-NOW+WiFi 동시 사용도(별도 코드 수정 없이, 어제 시도했던 채널 고정·초기화 순서 변경 등도 되돌린 원본 코드 그대로) 안정적으로 유지되는 것을 확인했다. 이는 오늘까지의 불안정 현상 대부분이 게이트웨이 코드의 결함이 아니라 **라즈베리파이 AP 모드 드라이버의 결함이었다**는 가설을 뒷받침한다.

전환 후 리프노드 4개(ext_01~04) 전체를 연결해 전체 파이프라인(리프노드 → ESP-NOW → 게이트웨이 → WiFi/UDP → 서버 → 대시보드)을 검증했고, 장시간 끊김 없이 정상 동작함을 확인했다.

## 예선과 결선에서의 통신 방식 차이

이 문제를 겪으며 명확히 정리된 것은, **WiFi 기반 통신은 예선까지의 임시방편일 뿐 결선(실제 대회장 배포) 방식이 아니라는 점**이다.

- **예선**: 시연 영상·GitHub·발표자료 제출 방식으로, 대회장 방문이 없다. 따라서 지금 검증한 "외부 공유기 클라이언트 모드" 구성으로 시연 영상을 촬영하는 것으로 충분하다.
- **결선**: 실제 대회장 현장에 시스템을 반입해 시연한다. 건물마다 WiFi 인프라가 상이하고, 있더라도 벽체 등으로 인한 RF 감쇠로 신뢰성 있는 무선 통신을 담보할 수 없다. 이에 따라 **고정 설비(자탐, 수계, 가스계, 유도등)는 RS-485 유선 통신으로 전환**하기로 결정했다(`docs/발전가능성_확장방안_정리_v2.md`의 실물 확장 로드맵과 같은 방향).

즉 오늘 다룬 ESP-NOW/WiFi 동시 사용 문제와 라즈베리파이 AP 모드 문제는 **예선 제출을 위한 임시 안정화**의 성격이며, 결선에서는 통신 계층 자체가 유선으로 바뀌어 이 문제군이 구조적으로 재발하지 않는다.

## 요약

| 문제 | 원인 | 대응 |
|---|---|---|
| 게이트웨이 WiFi 반복 끊김 | 라즈베리파이 `brcmfmac` 드라이버의 AP 모드 결함 | 라즈베리파이를 외부 공유기 클라이언트 모드로 전환 |
| ESP-NOW+WiFi 동시 사용 불안정 | ESP32 단일 라디오의 시분할 공유 구조적 제약 (AP 모드 결함과 중첩되어 증상이 악화됨) | AP 모드 결함 해소 후 재검증 결과, 원본 코드 그대로도 안정적으로 동작 확인 |
| 예선/결선 통신 방식 | 무선(WiFi)은 건물별 인프라 편차·RF 감쇠로 실물 배포 신뢰성 낮음 | 예선은 WiFi로 임시 진행, 결선은 RS-485 유선으로 전환 확정 |

디버깅 과정에서 "같은 증상(WiFi 끊김)"의 이면에 최소 두 개의 독립적인 원인(라즈베리파이 드라이버 결함, ESP32 무선 공유 제약)이 겹쳐 있었다는 점이 원인 규명을 어렵게 만들었다. 특정 코드 수정을 여러 차례 시도해도 재현이 계속됐던 것은, 더 상위 계층(라즈베리파이 AP 모드)의 결함이 해결되지 않은 상태에서는 하위 계층의 어떤 수정도 근본적으로 유효하지 않았기 때문으로 보인다.
