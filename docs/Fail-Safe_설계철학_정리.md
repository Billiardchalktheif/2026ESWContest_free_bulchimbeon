# 불침번 — Fail-Safe / Fool-Proof 설계 철학 정리

> 소방설비기사 실기에서 강조하는 Fail-Safe 원칙을 우리 시스템 설계에 대입한 자료입니다. 개발완료보고서 5~6번(차별성·파급력) 슬라이드 소재로 바로 활용 가능합니다.

---

## 핵심 문구 (발표자료 그대로 사용 가능)

> **"불침번 시스템은 소방공학의 핵심 원칙인 Fail-Safe를 설계 전반에 반영했습니다."**

세 가지 하위 원칙으로 구성됩니다:

| 원칙 | 한 줄 정의 | 우리 시스템 적용 |
|---|---|---|
| **Fail-Passive** | 실패해도 기존 기능을 방해하지 않음 | 모든 노드는 비침습(non-invasive) 방식 |
| **Fail-Active** | 실패를 침묵시키지 않고 능동적으로 알림 | 센서고장/통신두절을 화재와 구분해 별도 경보 |
| **Fail-Soft** | 일부 기능이 죽어도 핵심 기능은 저하된 채로라도 유지 | 로컬 경보 유지, 데이터 유실 방지 |

---

## 1. Fail-Passive — 노드가 죽어도 소방설비 본연 기능엔 무영향

**핵심 문구**: *"저희 노드가 완전히 파손되거나 전원이 꺼져도, 기존 소방시설 본연의 화재 경보 및 기동 기능에는 영향을 주지 않도록 설계되었습니다."*

### 이미 구현됨 — 새로 만들 것 없음 (문서화만 하면 됨)

모든 모듈이 **처음 설계 단계부터 비침습(tap) 방식**으로 되어 있었습니다:

| 모듈 | 비침습 방식 |
|---|---|
| 유도등 | 배터리 단자에 병렬로 전압만 측정, 원래 회로는 그대로 |
| 수계 | T피팅으로 압력만 곁다리 측정, 배관 흐름 자체엔 개입 안 함 |
| 가스계 | 저장용기를 저울 위에 얹기만 함, 용기·밸브 구조 변경 없음 |
| 소화기 | 가속도센서 부착만, 소화 매커니즘엔 손대지 않음 |
| 자탐 | 루프에 병렬 tap, 기존 수신기·감지기 회로 그대로 |

**할 일**: 코드 작업 없음. 발표자료에 위 표 그대로 넣고 "설계 초기부터 이 원칙을 지켰다"고 서술.

## 2. Fail-Active — 실패를 침묵시키지 않고 능동적으로 알림

### 2-1. 센서 고장(Fault) vs 화재 구분

**문제**: 센서 값이 0V로 뚝 끊기거나 비정상적으로 튀는 경우, 이를 "화재"로 오판하거나 반대로 무시하면 안 됨.

**해결 — 판정 로직 앞에 물리적 타당성 검사 한 단계 추가**

```python
# judge/rules.py — 기존 판정 로직 앞에 삽입
def check_sensor_fault(value, valid_min, valid_max):
    """
    센서값이 물리적으로 말이 안 되는 범위면 'fault'로 분류.
    화재/정상 판정 이전에 항상 먼저 거치는 관문.
    """
    if value is None or value <= valid_min * 0.01 or value >= valid_max * 1.5:
        return "sensor_fault"
    return None  # 정상 범위, 기존 판정 로직으로 진행

# 사용 예 (자탐 온도센서)
fault = check_sensor_fault(temp_c, valid_min=-10, valid_max=100)
if fault:
    status = "센서고장"
    send_alert(module="자탐1", level="fault", message="온도센서 이상(단선 의심)")
else:
    status = judge_fire_alarm(temp_c, ...)  # 기존 로직 그대로
```

**변경 범위**: 기존 규칙/회귀/AI 구조를 안 건드리고, **판정 전에 if문 한 단계만 추가**하는 수준. 서버 아키텍처 변경 없음.

### 2-2. Heartbeat 기반 통신두절 감지

**⚠️ 참고**: 이건 이미 이전 검토(`피드백_종합_반영여부_정리.md`)에서 **"결선 단계 최우선 후보"**로 지정해뒀던 항목입니다. 새로 결정할 게 아니라 이미 계획에 있었다는 걸 재확인한 것뿐입니다.

**개념**: 각 ESP32가 일정 주기로 "나 살아있다" 신호(heartbeat)를 보내고, 서버가 일정 시간(예: 10초~수 분) 이상 못 받으면 그 노드를 "정상"이 아니라 "통신두절"로 전환.

**현재 상태**: 예선에서는 스코프 아웃, 결선 단계에서 구현 예정.
**할 일 (지금 당장은 없음)**: 발표자료에 "결선까지 확장 예정"으로만 언급.

## 3. Fail-Soft — 일부가 죽어도 핵심 기능은 저하된 채로 유지

### 3-1. ESP32 하드웨어 워치독 (Watchdog Timer)

**문제**: 펌웨어가 락(무한루프 등)에 걸려 멈추면, 그 노드는 재부팅 전까지 계속 죽어있는 상태.

**해결**: ESP32 자체 내장 기능인 워치독 타이머를 켜두면, 일정 시간 응답이 없을 시 **자동으로 스스로 리셋**됩니다.

```cpp
// 각 .ino 파일의 setup()에 추가
#include "esp_task_wdt.h"

void setup() {
  esp_task_wdt_init(30, true);  // 30초 동안 응답 없으면 리셋
  esp_task_wdt_add(NULL);
  // ... 기존 setup 코드
}

void loop() {
  esp_task_wdt_reset();  // 정상 동작 중임을 계속 알림 (루프 맨 위에 추가)
  // ... 기존 loop 코드
}
```

**변경 범위**: 서버 코드는 전혀 안 건드림. 각 `.ino` 펌웨어에 몇 줄만 추가. 6개 모듈 코드에 각각 적용하면 됨(반복작업이라 부담 적음).

### 3-2. 로컬 플래시 버퍼링 (SPIFFS/LittleFS)

**⚠️ 참고**: 이것도 이미 결선 단계로 분류해뒀던 항목입니다.

**개념**: 통신이 끊긴 동안 ESP32가 데이터를 안 버리고 플래시 메모리에 임시 저장했다가, 통신 복구되면 한꺼번에 전송.

**현재 상태**: 예선 스코프 아웃 유지, 결선 단계에서 구현 예정.

## 4. 보너스 — Fool-Proof (점검자 실수 방지)

### 4-1. 가스계 캘리브레이션 락 (선택, 시간 되면)

**개념**: 로드셀 영점(Tare) 잡을 때, 흔들리는 상태에서 실수로 영점이 잡히는 걸 방지.

```python
# 캘리브레이션 루틴에 안정성 체크 추가
def is_stable(readings, threshold_g=0.1, duration_sec=3):
    """최근 readings가 duration_sec 동안 threshold_g 이내로 안정적인지 확인"""
    if len(readings) < duration_sec:
        return False
    recent = readings[-duration_sec:]
    return (max(recent) - min(recent)) <= threshold_g

# 영점 버튼 눌렀을 때
if is_stable(recent_weight_readings):
    perform_tare()
else:
    show_message("무게가 안정될 때까지 기다려주세요")
```

**우선순위**: 낮음, 여유 있으면 추가.

### 4-2. QR 점검이력 GPS/NFC 위치 검증 — 스코프 아웃

**판단**: 앱(GPS) + 서버(위치대조) + 하드웨어(NFC/BLE 비콘)까지 새로 필요해 지금 리소스로는 무리. **발전가능성 문서에 향후 확장 아이디어로만 기재.**

## 6. 정리 — 실제로 할 일 (친구에게 전달)

| 작업 | 대상 | 부담도 |
|---|---|---|
| 센서 fault 분류 if문 추가 | 서버 `judge/rules.py` | 낮음 (판정 로직 구조 안 바뀜) |
| ESP32 워치독 타이머 | 각 `.ino` 6개 | 낮음 (반복 작업, 몇 줄씩) |
| (선택) 가스계 캘리브레이션 락 | 서버 가스계 캘리브레이션 함수 | 낮음 |
| 무전원 비침습 구조 | 없음 | 문서화만 |
| Heartbeat/플래시버퍼링 | 없음 (결선으로 이미 확정) | 지금 안 함 |
| GPS/NFC Fool-Proof | 없음 | 지금 안 함, 발전가능성 문서에만 |

**서버 아키텍처(receiver/storage/judge/dispatch 구조) 자체는 전혀 안 바뀝니다.** 가장 부담되는 건 "센서 fault 분류"랑 "워치독" 두 개인데, 둘 다 기존 구조에 곁다리로 붙이는 수준이라 친구 부담은 크지 않을 것 같습니다.
