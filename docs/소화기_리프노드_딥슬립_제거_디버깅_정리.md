# 소화기 리프노드(ESP32-C3 SuperMini) — 딥슬립 구조 폐기 디버깅 정리

> 하드웨어 기술문서 "문제해결/트러블슈팅" 섹션에 삽입용. 리프노드 0번(`extinguisher_leafnode.ino`)이
> 딥슬립+MPU 인터럽트 웨이크업 구조에서 반복적으로 부팅/웨이크업 실패를 겪다가, 최종적으로
> **딥슬립 구조 자체를 폐기하고 상시 폴링 구조로 전환**하며 해결된 과정을 정리한다.

## 배경

리프노드는 배터리(리튬폴리머) 구동을 전제로, 평상시 딥슬립 상태를 유지하다가 MPU6500 가속도
인터럽트로 깨어나 이동/충격 이벤트만 ESP-NOW로 전송하는 구조로 설계됐다. 그러나 이 구조를
실제 SuperMini 보드에 이식하는 과정에서 연쇄적으로 문제가 발생했고, 개별 버그를 하나씩 고칠
때마다 새로운 층위의 문제가 드러나는 패턴이 반복됐다.

## 발견된 문제와 해결 순서

### 1. 워치독 타이머 API 불일치 (컴파일 에러)
아두이노 ESP32 코어 3.x(ESP-IDF 5 기반)로 넘어오면서 `esp_task_wdt_init()`의 시그니처가
`(uint32_t timeout_s, bool panic)`에서 `const esp_task_wdt_config_t*` 구조체 인자로 바뀌었다.
추가로 프레임워크가 이미 TWDT를 초기화해둔 상태(`ESP_ERR_INVALID_STATE`)일 수 있어
`esp_task_wdt_reconfigure()`로 방어하는 패턴을 전 노드 공통으로 적용했다.

### 2. ext1 웨이크업 API 부재 (컴파일 에러)
`ESP_EXT1_WAKEUP_ANY_HIGH`가 ESP32-C3에서는 선언조차 안 되어 있었다. 원인은 C3가 클래식
ESP32/S2/S3와 달리 **ext0/ext1 RTC-IO 딥슬립 웨이크업 하드웨어 자체가 없는 칩**이기 때문
(코드 주석의 "ext1을 하나의 핀만 써서 사용" 설명은 애초에 틀린 전제였음). 대체 API
`esp_deep_sleep_enable_gpio_wakeup(mask, ESP_GPIO_WAKEUP_GPIO_HIGH)`로 교체.

### 3. COM 포트 불안정 / 인식 실패
전송핀을 바꿔가며 재현을 시도했으나 단일 원인을 특정하지 못함. 케이블/포트 교체, 드라이버
재설치, 장시간 켜둔 PC 재부팅 등 일반적인 조치로 우회.

### 4. MPU6500 인터럽트 레지스터 버그
`INT_PIN_CFG`(0x37) 레지스터를 `0xA0`(active-low + latch)로 설정해뒀으나, 코드 주석은
"active-high"라고 적혀 있고 실제 ESP32 웨이크 조건도 `GPIO_WAKEUP_GPIO_HIGH`(HIGH 레벨)를
기대하고 있어 논리적으로 어긋나 있었다. `0x20`(active-high + latch)으로 수정.

### 5. `HWCDCSerial` 컴파일 에러
원인을 단일하게 특정하지 못했으나, 빌드 캐시 초기화 + 보드 패키지 재설치 + "USB CDC On
Boot" 설정 토글로 우회.

### 6. Native USB CDC 재연결 타이밍 레이스
ESP32-C3는 UART 브릿지 칩이 없는 Native USB 구조라, 딥슬립 진입 시 USB 포트 자체가 사라지고
깨어날 때 재열거(re-enumerate)된다. `setup()` 실행 후 딥슬립까지 100~200ms밖에 안 걸리는
구조라, 시리얼 모니터가 재연결되기 전에 이미 한 사이클이 끝나버려 로그를 못 보는 문제가
지속적으로 발생했다.

- `while (!Serial) delay(10)` 가드를 추가했으나, **arduino-esp32 core 3.3.5+에서 이 가드가
  신뢰성 있게 동작하지 않는 회귀 버그**가 있음을 GitHub Issue #12168로 확인.
- 임시 우회책으로 딥슬립 진입 직전 5초간 반복 출력하는 디버그 루프를 추가해 관찰 창을 확보.

### 7. "USB CDC On Boot" 설정 오해
디버그 과정에서 이 설정을 껐다 켰다 했는데, Disabled 상태에서는 `Serial`이 Native USB가 아닌
물리 UART0로 라우팅되어 "ROM 배너는 뜨는데 앱 로그가 전혀 안 뜨는" 증상이 나타남. 최종적으로
Enabled로 확정.

### 8. 플래시 손상 의심 → 배제
반복된 불안정 업로드 이력 때문에 플래시 손상을 의심해 "Erase All Flash Before Sketch
Upload"로 전체 삭제 후 재업로드했으나(해시 검증 성공), 증상 변화 없음 → 플래시 문제는 배제.

### 9. **GPIO2 부트 스트래핑 핀 충돌 (핵심 원인)**
`MPU_INT_PIN`이 GPIO2에 물려 있었는데, **GPIO2는 ESP32-C3의 부트 스트래핑 핀**이다. 리셋
시점에 이 핀의 전기적 상태로 부팅 모드를 판정하는데, 외부 MPU 인터럽트 라인이 여기 직결돼
있으면 그 순간의 전압 상태에 따라 비결정적으로 부팅 자체가 실패할 수 있다. 이 판정은 플래시를
읽기도 전에 일어나므로 **플래시 삭제/재업로드로는 절대 해결되지 않는다**는 게 8번 단계에서
증상 불변으로 나타난 이유였다.
- 근거: esptool 공식 "Boot Mode Selection" 문서, espboards.dev 스트래핑 핀 가이드
- 조치: `MPU_INT_PIN`을 스트래핑이 아닌 GPIO4로 이전 (배선 + 코드 상수 둘 다 변경)

### 10. 플로팅 핀 후속 문제
GPIO2를 비우고 나니, 아무것도 안 물린 플로팅 상태 자체도 부팅 스트래핑 판정 시 전압이
불안정해 문제가 될 수 있음이 확인됨. 안 쓰는 스트래핑 핀은 GND로 확실히 묶어두는 게 공식
권장 사항이라 GPIO2를 GND에 연결.

### 11. EN/RST 핀 오배선 근접 사고
GND 결선 작업 중 한때 "ROM 배너조차 안 뜨는" 상태로 악화됐는데, 컴팩트한 SuperMini 보드의
실크스크린에서 EN/RST 핀과 GND 핀이 물리적으로 인접해 헷갈리기 쉬운 게 원인으로 의심됨. 배선
재확인 후 정상화.

### 12. `Wire.begin()` 호출 순서 버그
디버그 코드(WHO_AM_I 출력, 워치독 설정)를 추가하는 과정에서 `Wire.begin(MPU_SDA_PIN,
MPU_SCL_PIN)` 호출이 실수로 **첫 I2C 통신(WHO_AM_I 읽기)보다 아래로 밀려 내려감**. I2C가
초기화되기 전에 `Wire.beginTransmission()`을 호출하면 정의되지 않은 동작(사실상 행)이
발생해, "ROM 배너만 뜨고 그 뒤로 아무 것도 안 뜨는" 증상으로 재현됨. 호출 순서를 바로잡아
해결 — `WHO_AM_I: 0x70` 정상 출력 확인.

### 13. 딥슬립-웨이크업 관측 불가 문제
1~12번을 전부 해결한 뒤 인터럽트 신호 자체(`digitalRead(MPU_INT_PIN)`)는 흔들 때 정상적으로
0→1 토글되는 것까지 확인했으나, "리셋을 눌러야만 잠깐 동작하고 흔들기만 해서는 반응이 안
보인다"는 증상이 남음. 이는 6번 항목(Native USB CDC 재연결 레이스)이 여전히 남아있던 것으로,
실제로는 웨이크업 자체는 되고 있었으나 PC 시리얼 모니터가 그 순간을 못 따라잡고 있었을
뿐이었음 — 게이트웨이 쪽 로그(가속도 값이 매 사이클 다르게 찍힘)로 간접 확인.

## 최종 결정 — 딥슬립 구조 자체를 폐기

위 13개 항목 중 상당수(2, 6, 7, 9, 10, 11, 13)가 전부 "딥슬립"이라는 요구사항 하나에서
파생된 문제였다. 근본 원인을 하나씩 대증치료하기보다, **애초에 딥슬립이 꼭 필요한
전제였는지**를 재검토했다:

- 배터리가 리튬폴리머 + TP4056 충전 모듈 조합으로 **상시 재충전이 가능**함
- 이 프로젝트는 장기 무인 현장 배치가 아니라 **경진대회 시연**이 목적 — 몇 달짜리 배터리
  수명보다 시연 중 안정 동작이 우선순위가 높음

이 두 조건이 맞아떨어져, 딥슬립 + MPU 하드웨어 모션 인터럽트 웨이크업 구조를 완전히 폐기하고
**상시 구동 + 소프트웨어 폴링 방식**으로 전환했다.

### 신규 구조 (v3)
- `esp_sleep.h`, `esp_deep_sleep_enable_gpio_wakeup()`, `RTC_DATA_ATTR`, MPU 하드웨어 모션
  인터럽트 레지스터(`INT_PIN_CFG`/`MOT_THR`/`MOT_DUR`/`INT_ENABLE`) 전부 제거
- `loop()`에서 200ms 주기로 가속도를 직접 폴링해 소프트웨어로 임계값 비교
  (`ACCEL_THRESHOLD_MS2`, 실측 후 튜닝 필요)
- 임계값 초과 시 즉시 전송(2초 쿨다운으로 스팸 방지) + 움직임 없어도 60초마다 하트비트 전송
- 워치독 패턴을 나머지 6개 노드와 동일하게 통일 (`loop()` 매 반복 `esp_task_wdt_reset()`)
- GPIO4-MPU INT 배선은 물리적으로 남겨둬도 무방하나 코드에서는 더 이상 사용하지 않음

### 부수 효과
- Native USB CDC 포트가 계속 연결 상태를 유지해 디버깅이 훨씬 쉬워짐
- 부트 스트래핑 핀 관련 제약 자체가 무의미해짐(딥슬립 웨이크 소스가 없으므로)

## 관련이지만 별개인 문제 — ESP-NOW/WiFi 채널 불일치

딥슬립 제거와는 별개로, 리프노드→게이트웨이 ESP-NOW 패킷이 도달하지 않는 문제가 병행
확인됐다. 원인은 게이트웨이가 실제 WiFi AP에 연결되며 배정받는 채널과, WiFi STA 모드만
초기화하고 AP에는 연결하지 않는 리프노드의 기본 채널(1번)이 서로 달라 802.11 MAC 레벨에서
패킷 자체가 도달하지 못하는 것 (자세한 내용은 `ESP-NOW_WiFi_채널_불일치_진단.md` 참고).
양쪽 모두 `esp_wifi_set_channel()`로 동일 채널 고정 + `peerInfo.channel` 명시로 해결.
