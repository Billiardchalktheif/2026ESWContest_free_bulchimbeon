# 네트워크 인프라 — 장애요인과 해결방안

> `docs/개발_장애요인_해결방안_정리.md`(설비별 하드웨어 장애요인 정리)와 같은 형식으로, 라즈베리파이 자체 WiFi 핫스팟(`BulchimbeonAP`) 인프라에서 겪은 문제를 정리한 자료입니다. 5개 설비 전체가 이 통신 인프라 위에서 동작하므로, 개별 설비 장애요인과 별도로 공통 인프라 항목으로 다룹니다.

---

## 1. 핫스팟 비영속성 (재부팅 시 소실)

### 장애요인: 임시 프로필로 생성된 핫스팟이 재부팅하면 사라짐
현장 배포 시 라즈베리파이는 인터넷이 없는 고립 환경에서 자체 WiFi 핫스팟(AP)으로 7개 노드를 수용해야 한다. 초기에는 `nmcli device wifi hotspot` 명령 한 줄로 핫스팟을 생성했으나, 이 방식은 `autoconnect` 속성이 꺼진 임시 연결 프로필을 만들기 때문에 전원을 껐다 켜면 핫스팟이 자동으로 복구되지 않았다. 시연 현장에서 전원 재인가가 발생하면 관리자가 매번 수동으로 SSH 접속 후 재실행해야 하는 상황이었다.

**해결방안**: `nmcli connection add`로 `autoconnect=yes`, `autoconnect-priority=100`을 명시한 영구 연결 프로필을 별도 생성. 소프트 리부트(`reboot`)와 완전 전원차단(콘센트 분리 후 재인가) 두 시나리오 모두에서 핫스팟이 자동 기동됨을 확인했다.

## 2. WiFi 클라이언트(ESP32) 인증 실패

### 장애요인: 신호가 완벽해도 특정 클라이언트만 연결이 거부됨
소화기 게이트웨이 노드가 스캔 결과에서 `BulchimbeonAP`를 RSSI -18dBm(최상급 신호)으로 정상 인식하면서도, 15초 연결 재시도 내내 인증에 실패하는 현상이 발생했다. 이미 실측 검증이 끝난 자탐1 노드로 교차 테스트해도 동일한 실패가 재현되어, 특정 보드의 하드웨어 결함이 아니라 AP 측 설정 문제임을 특정했다.

원인은 `nmcli`로 핫스팟을 생성할 때 `wifi-sec.proto`/`pairwise`/`group` 값을 지정하지 않으면 NetworkManager가 이를 WPA1/WPA2 혼합 협상이 가능한 상태로 남겨두는데, 노트북(Windows)의 WiFi 스택은 이 혼합 협상을 문제없이 처리하는 반면 ESP32의 WiFi 스택은 이 협상 단계에서 계속 실패한다는 점이었다. 스캔(수신)은 정상 동작하지만 실제 연결(양방향 협상)만 실패하는 증상이 이 원인을 특히 찾기 어렵게 만들었다.

**해결방안**: 핫스팟 프로필의 보안 방식을 `wifi-sec.proto=rsn`, `wifi-sec.pairwise=ccmp`, `wifi-sec.group=ccmp`로 명시해 순수 WPA2-CCMP로 고정. 채널도 혼잡 가능성이 있는 1번 대신 6번으로 고정하고, 절전모드(`802-11-wireless.powersave`)도 비활성으로 프로필에 박아두었다. 재구성 직후 ESP32의 정상 DHCP 발급과 데이터 수신을 확인했다.

## 3. 시스템 시계 리셋으로 인한 하트비트 오판정

### 장애요인: 인터넷 없는 AP 모드에서 시계가 과거로 고정됨
라즈베리파이 4는 RTC(실시간 시계) 배터리가 없어, 부팅 시 인터넷을 통한 NTP 동기화로만 정확한 시각을 얻는다. 그러나 현장 배포 환경은 자체 핫스팟(인터넷 없음) 상태이므로, 재부팅할 때마다 마지막으로 알고 있던 과거 시각(예: 8월 8일)에서 시계가 멈춰버렸다.

이 문제는 단순 로그 타임스탬프 표기 이상의 영향을 미쳤다. 온라인/오프라인 판정 로직(`is_node_online()`)이 `현재시각 - 마지막수신시각 <= 타임아웃`을 비교하는데, 현재시각이 마지막수신시각보다 과거로 뒤집히면서 그 차이가 음수가 되었고, 음수는 어떤 타임아웃 값보다도 작기 때문에 **전원이 꺼진 장비도 대시보드에서 전부 online으로 표시**되는 오판정이 발생했다.

**해결방안**: `fake-hwclock` 패키지를 설치하고 5분 주기 cron(`*/5 * * * * /sbin/fake-hwclock save`)으로 마지막 알려진 시각을 지속적으로 저장하도록 구성. 재부팅 시 이 저장된 시각으로 복원되어, 최소한 시계가 과거로 크게 역행하는 상황은 재발하지 않도록 했다. 완전한 실시간 정확도는 아니므로, 현장 배포 전 최초 1회는 유선/테더링으로 NTP 동기화를 거치는 절차를 체크리스트에 반영했다.

## 요약

| 문제 | 증상 | 근본 원인 | 해결 |
|---|---|---|---|
| 핫스팟 비영속성 | 재부팅하면 AP 사라짐 | 임시 프로필의 autoconnect 미설정 | 영구 프로필 + autoconnect 명시 |
| ESP32 인증 실패 | 신호는 잡히는데 연결만 실패 | WPA 프로토콜 협상 모호성 | WPA2-CCMP 명시 고정 |
| 하트비트 오판정 | 꺼진 장비가 online으로 표시 | RTC 부재 + 시계 역행 | fake-hwclock 주기 저장 |

세 문제 모두 개별로는 사소해 보이지만, 서로 인과관계 없이 동시에 겹치면서 원인 규명에 상당한 시간이 소요됐다. 특히 2번 항목은 소거법으로 SSID·비밀번호·신호세기·채널·접속대수·ESP-NOW 초기화 순서·보드 하드웨어까지 배제한 뒤에야 프로토콜 협상 문제로 좁혀졌으며, 이 경험을 바탕으로 "스캔은 되는데 연결만 실패"하는 증상은 보안 프로토콜 협상 문제를 우선순위 앞쪽에 두고 확인하는 것으로 팀 내 디버깅 순서를 갱신했다.
