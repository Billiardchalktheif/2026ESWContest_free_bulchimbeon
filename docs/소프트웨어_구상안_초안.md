# 불침번 소프트웨어 구상안 (Claude 초안)

> 친구 자료 오면 비교용으로 참고하세요. 출력은 대시보드/LCD/부저 3종 기준으로 설계했습니다.

---

## 1. 전체 계층 구조

```
[센서] → [ESP32 펌웨어] → [통신] → [라즈베리파이 서버] → [출력 3종]
                                         │
                              ┌──────────┼──────────┐
                          데이터저장    판정엔진      출력 디스패치
                          (DB)      (규칙+회귀+AI)   (대시보드/LCD/부저)
```

**설계 원칙**: ESP32는 "측정 + 최소한의 로컬 판정 + 전송"만 하고, 진짜 판단(추세분석, AI분류, 알림 결정)은 전부 라즈베리파이에서 처리합니다. ESP32가 죽어도 서버는 마지막 데이터를 기억하고, 서버가 재시작돼도 ESP32는 계속 측정해서 다시 보내는 느슨한 결합 구조입니다.

---

## 2. ESP32 펌웨어 구조 (모듈 공통 템플릿)

모든 모듈(자탐/수계/가스계/소화기/유도등)이 아래 틀을 공유합니다. 센서 읽는 함수만 모듈별로 다릅니다.

```
setup()
  ├─ WiFi 연결 (또는 ESP-NOW 초기화 — 소화기 리프노드만)
  ├─ 센서 초기화 (ADS1115, HX711 등)
  └─ 이전 상태 불러오기 (있다면)

loop()
  ├─ read_sensors()          # 모듈별로 다름
  ├─ local_check()           # 간단한 이상치 필터링 (예: 센서값이 물리적으로 말이 안 되면 무시)
  ├─ build_packet()          # JSON 형태로 포장
  ├─ send_packet()           # UDP 전송 (소화기는 ESP-NOW)
  └─ sleep(interval)         # 모듈별 주기 (자탐: 수 초, 소화기: 인터럽트+1시간)
```

**모듈별 read_sensors() 예시**
- 자탐1: `{온도, 온도상승률, 루프저항}`
- 자탐2: `{가스농도, 습도, 루프저항}`
- 수계: `{압력, CT전류(충압), CT전류(주펌프)}` + 이벤트성 `{체절압, 부하압}` (시험 실행 시)
- 가스계: `{중량}`
- 소화기(리프노드): 평소 무전송(딥슬립), 인터럽트 시 `{가속도이벤트=true}` 1회 전송
- 유도등: `{배터리전압×4, 조도×4}` (멀티플렉서 순회)

## 3. 통신 프로토콜 (패킷 포맷)

JSON으로 통일 — 사람이 읽기 쉽고 라즈베리파이에서 파싱 라이브러리 그대로 씁니다.

```json
{
  "module": "jatam1",
  "node_id": "jatam1_esp32",
  "timestamp": 1735689600,
  "data": {
    "temp": 24.3,
    "temp_rate": 0.8,
    "loop_resistance": 1024
  }
}
```

소화기(ESP-NOW)는 페이로드 크기 제한이 있어서 더 짧게:
```json
{"id":"ext_01","event":"accel_trigger","ts":1735689600}
```

게이트웨이가 이걸 받아서 위와 같은 JSON 포맷으로 감싸 UDP로 재전송합니다.

## 4. 라즈베리파이 서버 구조

```
server/
├─ main.py                 # 진입점 — 아래 세 스레드를 실행
├─ receiver/
│   ├─ udp_listener.py      # UDP 소켓으로 패킷 수신
│   └─ packet_parser.py     # JSON 파싱 + 모듈 라우팅
├─ storage/
│   ├─ db.py                # SQLite 연결/쿼리 함수
│   └─ schema.sql           # 테이블 정의
├─ judge/
│   ├─ rules.py             # 규칙 기반 판정 (법정 기준값 비교 — 가스계(CO2) 10%, 수계 140%/65% 등)
│   ├─ regression.py        # 추세 예측 (numpy.polyfit — 자탐 배선, 유도등 배터리)
│   └─ ai_models/
│       ├─ jatam2_classifier.pkl   # 자탐2 오작동 판별 모델
│       └─ pump_classifier.pkl     # 수계 펌프 파형 분류 모델
├─ dispatch/
│   ├─ dashboard_api.py     # 대시보드에 데이터 제공 (REST API 또는 WebSocket)
│   ├─ lcd_output.py        # LCD 표시 제어
│   └─ buzzer_output.py     # 부저 경보 제어
└─ config.py                # 임계값, 핀 번호 등 설정값 모음
```

**처리 흐름 (판정엔진)**
```
1. udp_listener가 패킷 수신
2. packet_parser가 모듈 식별 후 storage/db.py로 원본 저장
3. judge/ 모듈이 최신 데이터 + 과거 데이터 불러와서:
   - rules.py: "지금 이 값이 기준치를 넘었나?" (즉시 판정)
   - regression.py: "추세대로면 언제 기준치 도달?" (자탐/유도등/가스계)
   - ai_models: "이 패턴이 정상/이상 중 뭐야?" (자탐2, 수계)
4. 판정 결과를 다시 DB에 저장 (상태 이력 관리)
5. dispatch/가 결과에 따라 세 출력을 갱신
```

## 5. DB 스키마 (간단안)

```sql
-- 원본 센서 로그
CREATE TABLE sensor_log (
    id INTEGER PRIMARY KEY,
    module TEXT,
    node_id TEXT,
    timestamp INTEGER,
    payload TEXT       -- JSON 그대로 저장 (모듈별 필드가 달라서)
);

-- 판정 결과 (모듈별 현재 상태)
CREATE TABLE status (
    module TEXT PRIMARY KEY,
    state TEXT,          -- 'normal' / 'warning' / 'critical'
    detail TEXT,          -- 사람이 읽을 설명 ("3층 자탐 루프저항 상승 추세")
    updated_at INTEGER
);

-- 이벤트 이력 (경보 발생 기록, 나중에 리포트용)
CREATE TABLE event_log (
    id INTEGER PRIMARY KEY,
    module TEXT,
    level TEXT,
    message TEXT,
    timestamp INTEGER
);
```

## 6. 출력 3종 처리 방식

### ① 대시보드 (친구 제작분과 연동)
서버가 **REST API 몇 개**를 열어두고, 대시보드가 주기적으로 조회(polling)하거나 WebSocket으로 실시간 push 받는 구조를 제안합니다.
```
GET /api/status           → 전체 모듈 현재 상태 (평면도 색상용)
GET /api/history/{module} → 특정 모듈의 시계열 데이터 (그래프용)
GET /api/events           → 최근 경보 이력
```
친구 쪽 대시보드가 이 API 스펙에 맞춰 데이터를 받아가는 방식이면, 서버 로직과 화면 UI가 독립적으로 개발 가능합니다.

### ② LCD (16x2 또는 20x4, I2C)
라즈베리파이 GPIO에 I2C로 직결 — 별도 ESP32 필요 없이 라즈베리파이가 바로 제어합니다.
- 평소: 5개 모듈 상태를 몇 초 간격으로 순환 표시 (`자탐: 정상 | 수계: 정상 | ...`)
- 경보 발생 시: 해당 모듈 내용으로 고정 표시 + 깜빡임

### ③ 부저 (능동 부저, 라즈베리파이 GPIO 직결)
경보 등급별로 패턴을 다르게:
- 주의(warning): 짧게 1번 삑
- 경보(critical): 연속 삑삑삑 + LCD 고정 표시와 동시 발생

## 7. 이 구상안의 특징 (팀 논의용 포인트)

- **ESP32는 최대한 단순하게, 판단 로직은 서버에 집중** — 나중에 로직 바뀌어도 ESP32 펌웨어 다시 안 올려도 되는 장점
- **판정엔진을 rules/regression/ai_models로 명확히 분리** — 발표자료 "함수별 기능" 항목에 그대로 대응 가능
- **LCD/부저를 라즈베리파이에 직결** — 별도 출력 전용 ESP32 안 만들어도 돼서 부품·배선 절약
- DB는 SQLite로 가볍게 — 라즈베리파이 2GB에서도 부담 없음

친구 소프트웨어 자료 오면 이 구조랑 비교해서 서로 다른 부분(예: DB 종류, 통신 방식, 폴더 구조)을 맞춰나가면 될 것 같습니다.
