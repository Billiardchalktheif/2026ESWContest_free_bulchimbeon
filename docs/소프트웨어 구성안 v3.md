# 불침번 소프트웨어 구성안 (v3 — 앱 실제 구현 반영)

> v2 대비 변경점: 네이티브 앱(Flutter) 파트가 **막 시작 단계**라는 걸 반영했습니다. 앱 담당이 받은 건 설정 가이드(`처음부터_시작하기_Windows.md`)와 기능 설계 가이드 (`네이티브앱_고급기능_가이드.md`) 2개뿐이고, 실제로 폰에 설치해서 돌려본 적은 아직 없습니다. API도 6개 엔드포인트가 **설계·목데이터 코드까지만** 있고 실제 하드웨어와의 연결은 전부 앞으로 할 일입니다. API는 대시보드와 합치지 않고 별도 프로세스(`api.py`, 포트 5001)로 갈 계획이며, 출력은 대시보드(화면) + 부저/LCD(현장) + 네이티브 앱(원격, 시연용) 3종, 앱은 안드로이드·Flutter·스토어 미제출로 방향만 확정된 상태입니다.

---

## 1. 전체 계층 구조

```
[센서] → [ESP32 펌웨어] → [통신] → [라즈베리파이 서버] → [출력 3종]
                                         │
                              ┌──────────┼──────────┐
                          데이터저장    판정엔진      출력 디스패치
                          (storage)   (judge)       (dispatch)
```

**설계 원칙**: ESP32는 "측정 + 전송"만 하고, 진짜 판단(추세분석, AI분류, 알림 결정)은 전부 라즈베리파이에서 처리합니다. ESP32가 죽어도 서버는 마지막 데이터를 기억하고, 서버가 재시작돼도 ESP32는 계속 측정해서 다시 보내는 느슨한 결합 구조입니다.

## 2. ESP32 펌웨어 구조 (모듈 공통 템플릿)

모든 모듈이 아래 틀을 공유합니다. 센서 읽는 함수만 모듈별로 다릅니다.

```
setup()
  ├─ WiFi 연결 (또는 ESP-NOW 초기화 — 소화기 리프노드만)
  ├─ 센서 초기화 (ADS1115, INA219, HX711 등)
  └─ 이전 상태 불러오기 (있다면)

loop()
  ├─ read_sensors()          # 모듈별로 다름
  ├─ local_check()           # 간단한 이상치 필터링
  ├─ build_packet()          # JSON 형태로 포장
  ├─ send_packet()           # UDP 전송 (소화기는 ESP-NOW)
  └─ sleep(interval)         # 모듈별 주기 (자탐: 수 초, 소화기: 인터럽트+1시간)
```

**모듈별 read_sensors()**

|모듈|읽는 값|인터페이스|
|---|---|---|
|자탐1(차동식)|온도, 온도상승률(dT/dt), 루프저항|ADS1115(I2C)|
|자탐2(광전식)|가스농도, 습도, 루프저항|ADS1115(I2C) + DHT22(디지털)|
|수계|압력, INA219 전류(충압/주펌프 각각)|I2C(0x40/0x41) + 아날로그(압력, 분압 후)|
|가스계|중량|HX711(디지털)|
|소화기(리프노드)|평소 무전송(딥슬립), 인터럽트 시 가속도 이벤트 1회|I2C + 인터럽트|
|유도등|배터리전압×4, 조도×4|멀티플렉서 경유 아날로그|

**⚠️ 수계 전류센서 주의**: CT클램프(비접촉, AC전용)는 우리 워터펌프가 DC 구동이라 사용 불가 — **INA219(I2C 션트저항 방식)**로 전선을 직렬로 끊어 삽입하는 방식을 씁니다. 펌프 2개가 같은 I2C 버스를 공유하므로 주소를 0x40/0x41로 분리합니다.

## 3. 통신 프로토콜 (패킷 포맷)

JSON으로 통일합니다.

```json
{
  "module": "jatam1",
  "node_id": "jatam1_esp32",
  "timestamp": 1735689600,
  "data": {
    "temp": 24.3,
    "temp_rate": 0.8,
    "loop_resistance": 1024
  }
}
```

소화기(ESP-NOW)는 페이로드 제한이 있어 더 짧게:

```json
{"id": "ext_01", "event": "accel_trigger", "ts": 1735689600}
```

게이트웨이가 이걸 받아 위 포맷으로 감싸 UDP로 재전송합니다.

## 4. 라즈베리파이 서버 구조

```
server/
├── main.py                     # 진입점
├── config.py                   # 임계값, I2C 주소, 상수 모음
├── feature_extraction.py       # 파형/전류 샘플 → RMS·peak·duty_cycle
├── pump_performance_test.py    # 밸브 시퀀스 실행 + AI 라벨 자동연동
├── receiver/
│   ├── udp_listener.py         # 소켓 수신 루프
│   └── packet_parser.py        # JSON 파싱 + 모듈 라우팅 + heartbeat
├── storage/
│   ├── db.py                   # SQLite 연결/쿼리 함수
│   └── schema.sql              # 테이블 정의
├── judge/
│   ├── rules.py                 # 규칙 기반 판정 (법정기준 비교 — 가스계 10%, 수계 140%/65%, 소화기 이탈)
│   ├── regression.py            # 추세 예측 (자탐 z-score, 유도등/가스계 회귀)
│   ├── classify.py              # AI 모델 로드 + 예측 (자탐2, 수계)
│   └── ai_models/
│       ├── pump_classifier.joblib
│       └── nuisance_classifier.joblib
└── dispatch/
    ├── lcd_buzzer_output.py     # I2C LCD + 부저 제어, trigger_alert() 공통 진입점
    └── api.py                    # 네이티브 앱용 REST API (신규, 착수 단계) — 별도 Flask
                                   # 프로세스(포트 5001)로 계획, 대시보드(app.py)와 포트 분리

app/            # 네이티브 앱 (Flutter, 안드로이드, 시연용 APK — 착수 단계, 설정 가이드만 있음)
```

**처리 흐름**

```
1. udp_listener가 패킷 수신
2. packet_parser가 모듈 식별 후 storage/db.py로 원본 저장, heartbeat 갱신
3. judge/가 최신+과거 데이터로 판정
   - rules.py: 기준치 즉시 비교
   - regression.py: 추세 기반 예측 (자탐/유도등/가스계)
   - classify.py: AI 패턴 분류 (자탐2, 수계)
4. 판정 결과를 다시 DB에 저장 (상태 이력)
5. dispatch/가 결과에 따라 LCD·부저 갱신, app_api.py의 엔드포인트에 최신값 반영
6. dashboard/가 DB를 읽어 화면에 렌더링 (Flask, 직접 HTML 렌더링 — API 분리 안 함)
7. (착수 단계) 네이티브 앱(Flutter)이 dispatch/api.py(포트 5001)의 6개 엔드포인트를
   폴링/호출해 상태·이력 표시, QR조회, PDF리포트, 원격 성능시험 트리거, 경보 확인, 부저
   음소거를 수행할 예정 — 지금은 설계·목데이터 코드 단계이고 실물 연결은 앞으로 진행
```

## 5. AI가 실제로 적용된 지점 — 정확히 2곳

|모듈|모델|판정 방식|
|---|---|---|
|수계|RandomForest|INA219 전류값 패턴 → 정상운전/체절운전/유량저하/공회전/기동실패 (5클래스)|
|자탐2|RandomForest|온도상승률+가스농도+습도 → 화재/조리연기/평상시|

**나머지(자탐1, 가스계, 유도등, 소화기)는 전부 규칙·회귀 기반**입니다. 안전 시스템은 판정 근거가 설명 가능해야 하고, 여러 값을 동시에 보고 패턴을 구분해야 하는 문제라는 공통점이 있는 이 두 곳만 예외로 AI를 적용했습니다.

## 6. DB 스키마 요지

```sql
-- 자탐 (1/2구역 공용, zone_type으로 구분)
CREATE TABLE fire_alarm_log (
    ts REAL, node_id TEXT, zone_type TEXT,
    loop_resistance_ohm REAL, temp_rise_rate REAL,
    mq2_raw REAL, humidity_pct REAL,
    label TEXT, predicted_label TEXT, status TEXT
);

-- 수계 (충압/주펌프 공용, pump_type으로 구분)
-- label/predicted_label 값 도메인: normal_operation(정상운전) / stall_operation(체절운전)
-- / flow_reduced(유량저하) / dry_run(공회전) / startup_failure(기동실패) — 5클래스
-- ("정상/과부하" 대신 물리적으로 확인된 실험 상태를 그대로 이름 붙임. 체절 시 전류가
-- 펌프 종류에 따라 낮게 나올 수 있어, 라벨명에 전류 높낮이를 내포하지 않도록 설계)
CREATE TABLE water_pump_log (
    ts REAL, node_id TEXT, pump_type TEXT,
    cycle_interval_sec REAL, rms REAL, peak REAL, duty_cycle REAL,
    valve_state TEXT, pressure_kpa REAL, rated_pressure_pct REAL,
    label TEXT, label_source TEXT, predicted_label TEXT
);

-- 가스계 (공병중량 차감 반영)
CREATE TABLE gas_log (
    ts REAL, node_id TEXT, weight_g REAL,
    initial_weight_g REAL, empty_container_weight_g REAL,
    loss_pct REAL, predicted_days_to_5pct REAL, gas_type TEXT
);

-- 소화기 (이탈감지)
CREATE TABLE extinguisher_log (
    ts REAL, node_id TEXT, accel_event INTEGER,
    gateway_id TEXT, status TEXT
);

-- 유도등 (캘린더 열화 vs 실제 방전 분리)
CREATE TABLE evac_light_log (
    ts REAL, node_id TEXT, battery_voltage REAL, lux INTEGER,
    predicted_days_to_replace REAL, estimated_discharge_min REAL, demo_mode INTEGER
);

-- 노드 생사 감시 (전 설비 공통)
CREATE TABLE node_heartbeat (
    node_id TEXT PRIMARY KEY, device_type TEXT,
    last_seen REAL, last_seq INTEGER, boot_id TEXT, status TEXT
);
```

## 7. 출력 3종

### ① 대시보드

Flask가 SQLite를 읽어 직접 HTML 렌더링. 5개 설비 카드 + heartbeat 상태 표시, 수 초 간격 자동 새로고침.

### ② 부저 + LCD (현장)

라즈베리파이 GPIO/I2C 직결. LCD(16x2 또는 20x4)에 평소 5개 설비 상태를 순환 표시하고, 경보 발생 시 해당 모듈 내용으로 고정+깜빡임. 부저는 경보 등급별로 패턴 구분:

- 주의(warning): 짧게 1번
- 경보(critical): 연속 삑삑삑 + LCD 고정 표시와 동시 발생

### ③ 네이티브 앱 (원격, 시연용 — 착수 단계)

Flutter, 안드로이드, **스토어 미제출·APK 직접 설치로 시연용** — 방향은 확정됐지만 아직 폰에 설치해서 돌려본 적은 없는 단계. `dispatch/api.py`(별도 Flask 프로세스, 포트 5001로 계획)에 6개 엔드포인트가 목데이터 기준으로 설계되어 있음:

|엔드포인트|용도|
|---|---|
|`GET /api/status`|5개 설비 현재 상태 (상태 탭)|
|`GET /api/events`|최근 경보 이력 (알림 탭)|
|`GET /api/equipment/<qr_id>`|QR 스캔 → 설비 이력 조회 (QR조회 탭)|
|`GET /api/report/pdf?days=N`|점검이력 PDF 리포트 생성 (도구 탭)|
|`POST /api/performance-test/trigger`|수계 원격 성능시험 트리거 (도구 탭) — **밸브는|
|여전히 수동이라 "펌프 기동·측정은 원격, 밸브 개폐는 현장"인 반자동으로 설계, 실물 연결은||
|미착수**||
|`POST /api/alerts/<id>/ack` · `POST /api/buzzer/mute`|경보 확인, 부저 음소거 (알림 탭)|

앱 화면은 상태/QR조회/알림/도구 **4개 탭으로 설계**. `MOCK_MODE`로 실물 하드웨어 없이 서버·앱을 먼저 검증하는 방식(지금까지 다른 모듈에서도 써온 "더미데이터로 파이프라인 먼저 검증" 원칙과 동일)으로 진행할 예정. 실시간 푸시(FCM 등)는 범위에서 제외 — 폴링만으로 원격 알림 컨셉 증명에 충분하다고 판단. 서버 주소는 앱의 `API_BASE_URL` 상수 하나로 관리되도록 설계되어, 배포 환경(개발 PC → 라즈베리파이) 전환이 간단할 것으로 예상.

## 8. 이 구조의 특징 (발표·보고서용 포인트)

- **ESP32는 최대한 단순하게, 판단 로직은 서버에 집중** — 로직이 바뀌어도 ESP32 펌웨어를 다시 올릴 필요가 대부분 없음
- **judge/를 rules·regression·classify로 명확히 분리** — "왜 이 설비엔 AI를 안 쓰고 저 설비엔 썼는지"를 코드 구조 자체로 설명 가능
- **CT클램프→INA219 전환**: DC/AC 측정 원리 차이를 실측으로 발견하고 대응한 과정 자체가 개발 장애요인 해결 사례로 보고서에 활용 가능
- **가스계 공병중량 차감**: 총중량이 아니라 약제중량 기준 계산으로 수정 — 미니어처 규모에서 특히 중요한 보정
- **폰 → 실제 물리적 동작 (계획)**: 원격 성능시험 트리거가 완성되면 "폰 버튼 → 실제 펌프 작동 → 데이터 기록"이라는 물리적 동작(actuation)이 시연에 생김. 밸브가 수동이라는 한계는 "솔레노이드 교체 시 완전자동 확장 가능"이라는 로드맵으로 정직하게 설명
- DB는 SQLite로 가볍게 — 라즈베리파이 2GB에서도 부담 없음
- 대시보드 API 분리, LCD 출력 등은 현재 범위에서 제외 — 개발 리소스 대비 이득이 크지 않다고 판단해 결선 이후 확장 검토 대상으로 남김
